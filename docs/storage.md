# 月度 JSON 分片存储

## 目标与范围

保留可检查、可导出的 JSON 数据，将记录按月份分片，减少日期查询和普通修改涉及的数据量；同时解决并发读改写覆盖、文件写入中断及跨文件恢复问题。

本实现适用于单机本地文件系统、多进程和多线程的部署方式。不支持多台机器通过共享网络文件系统同时写入，不引入独立数据库、分布式锁或新的前端数据格式。

## 数据布局

```text
data/
├── records.json
├── records/
│   ├── 2026-08.json
│   └── 2026-09.json
├── metadata.json
├── layout.json
├── supplement_settings.json
├── medicine_settings.json
├── fever_mode.json
├── reminder_state.json
├── .storage.lock
├── transactions/
│   └── pending.json
└── backups/
    ├── records_*.json
    ├── migration_*.json
    ├── snapshot_*.json
    └── before_restore_*.json
```

- `records/YYYY-MM.json`：该北京时间月份的记录数组。按记录发生时间分片，历史补录写入历史月份。无时区时间按北京时间解释；带时区时间先换算北京时间用于选择分片，但保存的时间字符串和其他字段不变。
- `metadata.json`：格式版本、月份清单和已提交记录版本。每次记录新增、编辑、删除和恢复生成一个新的不透明版本字符串。不要依赖版本字符串的具体格式。
- `layout.json`：已经初始化过分片存储的标记。即使所有记录都被删除，清单损坏或丢失也不会触发对旧 `records.json` 的重新导入。
- `transactions/pending.json`：包含目标文件完整新内容及校验和的恢复日志。正常提交后删除；存在时必须完成恢复后才能继续访问。
- `records.json`：只在首次迁移时读取，原文件保留作审计与迁移前回退依据。**迁移后它不再更新，不是实时数据源。** 新建的空分片存储不创建该文件。
- 设置文件继续使用原有格式，缺失时应用采用原来的默认设置。

不应手工增加、编辑、删除分片、清单、日志或运行中的锁文件。所有读取和修改必须使用 `storage.py` 或应用 API；读取分片的外部程序若不遵循锁协议，可能在跨文件提交中途看到不一致内容。

## 读写与一致性

`storage.py` 中的 `JsonRecordStore` 是唯一文件存储入口。`baby.py` 和 `reminder.py` 共用该实现。

1. 外层操作独立打开 `.storage.lock` 并取得排他文件锁；不同线程、不同进程的访问均串行化。同一线程在同一存储实例中的嵌套调用可以重入。
2. 取得锁后先重放未完成事务，再读取并校验清单。文件不可读、内容损坏、时间无效或重复 ID 都不能被当作空数据继续覆盖。
3. 新增、编辑、删除的业务校验和持久化处于同一锁范围内。补剂同日计划时段的校验与插入不会分离；修改补剂时间时也会重新检查目标日期的计划时段。
4. 提交前将涉及的分片、设置和新清单写入带校验和的事务日志，并同步落盘。随后各目标文件通过同目录临时文件、文件同步、原子替换和目录同步提交，清单最后替换。
5. 全部文件提交后删除日志并同步目录。若中途终止，下次访问会幂等重放同一份新内容，因此跨月移动不会永久停留在只删除源文件或只写入目标文件的状态。

HTTP 记录写入和带记录版本的读取在锁内构造结果与版本。分析缓存继续使用 `X-Records-Version`、响应中的 `version` 和 `/api/records/version`，不再依赖文件大小和修改时间。单独修改设置或提醒去重状态不更新记录分析版本。

写入返回成功前已完成文件与目录同步。若日志已落盘、后续磁盘操作失败，请求可能返回 503，但事务仍会在恢复时完成；**503 不代表该次新增一定没有保存，应先刷新确认，再决定是否重试。** 本实现不提供网络请求幂等键，也不保证外部语音播报恰好一次。外部播报请求不占用存储锁。

## 查询与兼容性

- `/api/records` 和 JSONP 仍返回完整记录数组；记录对象字段及原有排序方式保持兼容。
- 列表日期筛选先选择月份，再沿用原来对时间文本的前缀匹配语义。为兼容时区换算导致的跨月归属，月边界会补读邻近分片；普通月中日期只读所在月份。非完整日期前缀仍可回退到全量筛选。
- 喂养分析按所选日期和七天趋势的日期范围读取月份。睡眠分析仍合并全部分片，保留跨月入睡/醒来配对、历史未结束睡眠和睡姿累计规则。
- 首页综合数据、独立提醒脚本以及其他需要完整历史的调用暂时保留全量合并。不会简单假定最近一个月必然含有最后一次喂奶或尚未结束的睡眠。
- 新增只重写对应月份；跨月编辑只重写源、目标月份；最后一条记录删除后移除空分片并更新清单。
- 第一版 ID 查重、编辑及删除定位仍可能扫描历史分片。没有维护第二份需要同步提交的 ID 索引，因此不能将“只重写相关月份”理解为所有写入都只读取一个文件。
- HTTP 输入中的非法时间或非有限 JSON 数值返回 400；损坏的活动存储和 I/O 错误返回 503。不存在的记录和备份保持 404，补剂计划冲突保持 409。
- 旧 `records_*.json` 数组备份继续可以恢复，只替换记录并保留当前设置。新快照会同时恢复记录及设置。
- 查询技能使用 `/api/records`，不需要修改；任何自行读取旧 `records.json` 的外部脚本必须改用 API、共享存储模块或显式导出。

## 备份策略

- 每次成功写入后检查备份间隔；距最近普通快照至少一小时时，生成一个包含全部记录及四种设置文件的完整快照。无写入时不创建重复快照，不依赖另一个后台定时线程。
- 备份在同一存储锁内取得一致性数据，包含内容校验和。名称包括微秒及随机后缀，不会因同秒操作而重名。
- 普通 `snapshot_*.json` 保留最近 24 小时的快照、最近 14 天每天最新一份、最近 8 周每周最新一份。清理发生在创建普通快照之后。
- 首次导入前创建 `migration_*.json`；每次恢复前创建 `before_restore_*.json`。这两种保护快照与旧 `records_*.json` 不参与自动清理，需要运维另行归档。
- 普通自动备份失败会记录警告，但不会把已提交记录伪装成保存失败。首次迁移的保护备份和恢复前备份是必要步骤，失败会阻止该次迁移或恢复。
- 新快照文件是一个逻辑数据集，不包含旧备份目录及原始迁移文件。初次升级前仍需另外保存整个旧数据目录。
- 数据目录内的备份不能防止整块磁盘损坏。应将已经完成的快照或停服归档另外复制到受控的异机位置；本次没有配置外部存储地址、上传任务或凭据。

## 首次部署与迁移

**先停止旧版应用及所有旧写入脚本，再迁移。旧版不遵守新锁，也不会读取新分片，不能滚动混跑。** 普通存储访问会自动初始化、迁移或恢复，因此 `verify`、`backup` 和 `export` 也必须遵守首次升级的停写要求；不要在旧服务运行时直接对正式目录运行这些命令。

默认 Docker 数据目录仍是 `/app/data`，映射到宿主机 `./data`。建议使用容器内命令，保持与服务相同的 UID 和权限；原部署默认以 root 运行，部分现有设置已经是 root 所有，新原子文件默认权限为 `0600`。不要通过放宽所有文件权限来绕过读取问题。

在项目目录执行以下步骤；构建在停服前完成，以缩短停写时间：

```bash
docker compose build app
docker compose stop app
backup_path="../baby-data-before-sharding-$(date +%Y%m%d_%H%M%S).tar.gz"
umask 077
docker compose run --rm -T --no-deps --entrypoint tar app -C /app -czf - data > "$backup_path"
gzip -t "$backup_path"
docker compose run --rm --no-deps app python storage.py migrate
docker compose run --rm --no-deps app python storage.py verify
docker compose up -d --no-build app
```

逐条检查命令的退出状态；归档或迁移失败时不要继续启动。独立旧进程和定时任务也必须在停写期间停止，`docker compose stop app` 不会停止容器外的程序。

迁移会校验记录数组、非空字符串 ID、重复 ID、可解析时间及有效 JSON 数值，再按月份导入。发现无效记录会报告问题并停止，不会丢弃记录或猜测日期。原始 `records.json` 保留不变；无效记录应先在单独副本中核对和修正，再安排正式迁移。

成功后检查计数、月份、首页、记录列表和分析结果，并留存迁移前归档。再次运行 `migrate` 不会覆盖已经初始化的存储，只验证当前数据。

`BABY_DATA_DIR` 可为本地运行或隔离验证指定其他目录。`REMINDER_ENABLED=false` 可禁用后台提醒线程，默认仍启用；Docker Compose 已转发 `REMINDER_ENABLED`，存储命令本身不会启动提醒。

## 日常命令

部署完成后，在运行中的容器内执行：

```bash
docker compose exec app python storage.py verify
docker compose exec app python storage.py backup
docker compose exec app python storage.py export --output /tmp/baby-records-export.json
docker cp baby-app:/tmp/baby-records-export.json ./baby-records-export.json
```

导出仍是旧接口兼容的完整记录数组，但导出路径必须位于活动数据目录之外，避免覆盖清单或旧迁移源。导出不包含设置；完整恢复应使用快照。

指定快照恢复：

```bash
docker compose exec app python storage.py restore --filename snapshot_实际备份文件名.json
```

应用恢复接口保持 `POST /api/backup/restore`，请求示例为 `{"filename":"snapshot_实际备份文件名.json"}`。省略文件名时选择最新可用备份，排除恢复前保护快照；恢复前快照仍可通过明确文件名恢复。`GET /api/backup/list` 保持返回 `filename`、`size` 和 `time` 字段。

恢复会拒绝路径穿越、符号链接、内容校验失败、重复 ID、无效时间及不完整的新格式设置。记录与设置通过同一个可重放事务替换；旧清单中多余的月份和快照中不存在的设置文件会被移除，记录版本重新生成。

这些管理接口沿用现有应用的访问边界，本次没有新增认证机制。不要将服务或恢复接口无保护地暴露到不可信网络。

## 故障恢复与回滚

- **遗留事务**：不手工删除 `pending.json`。修复磁盘空间或权限后，让新版本读取存储或运行 `verify`，程序会先验证校验和并完成重放。成功后日志会报告恢复的事务 ID。
- **文件损坏或日志校验失败**：程序停止相应访问，不自动选取某个备份覆盖。先停服并原样归档整个损坏目录；不要只删除清单或锁文件试图重新初始化。
- **活动数据已损坏，无法制作恢复前快照**：在线恢复会拒绝继续，以免覆盖无法保存的现场。保留完整损坏目录后，创建另一个空数据目录，把选定完整快照放入其 `backups/`，通过 `storage.py restore --data-dir <新目录> --filename <文件名>` 恢复并执行 `verify`；确认正确后，在停服状态切换挂载目录，再启动服务。
- **回滚代码且没有新数据**：停服并保存当前目录，再恢复升级前的完整目录归档与旧代码/镜像。
- **回滚代码但已有新数据**：先停写，用新版本生成完整快照并导出当前记录；将导出的记录与对应设置还原到一个新的旧版数据目录，再切换旧代码/镜像。不能直接使用冻结的旧 `records.json`，也不能让旧版继续写入仍保留新清单的目录，否则将来再次升级会读到过期分片。

预留足够磁盘空间容纳目标分片的新副本、恢复日志及完整备份。全局锁优先保证正确性，长时间导出、完整备份和历史睡眠计算会暂时阻塞其他存储访问；规模进一步增长时再考虑可重建索引或更细粒度的锁。
